# AGENTS.md — Convenzioni per gli agenti su ScuolaBoard

Istruzioni operative per chi (umano o agente) modifica questo repository.
Quando un punto di questo file contraddice `README.md`, vince `README.md`.

## Lingua

- **Rispondi sempre in italiano**, sia nel testo verso l'utente sia nei commenti al codice.
- Messaggi di commit, issue, PR e documentazione sono in italiano (vedi la cronologia: `fix(classi,login): sblocco salvataggio…`).

## Panoramica

ScuolaBoard è una web app per la bacheca digitale scolastica (docenti + studenti):

- **Frontend**: React 18 + TypeScript, bundler **Vite**. `main.tsx` importa i moduli in ordine. Il JSX usa il runtime **automatico** (default di `@vitejs/plugin-react`), in test come in build: lo shorthand `<>` non ha bisogno di importare `React` né `Fragment`. ⚠️ Non reintrodurre `jsxRuntime: 'classic'` con `{ pragma: 'h', pragmaFrag: 'Fragment' }`: era in `vitest.config.js` e non ha mai avuto effetto, perché **Babel rifiuta pragma e pragmaFrag quando il runtime è automatico** ("pragma and pragmaFrag cannot be set when runtime is automatic"). Verificato in tre modi: trasformazione Babel diretta, rimozione di `import { Fragment }` senza rotture, e bundle di produzione che chiama `(0, jsxs)('div', …)`. La guardia `src/no-bare-react.test.ts` resta utile (i moduli legacy usano il global `window.React`), ma non perché il runtime lo richieda.
- **Backend dati**: **Firestore** (non Realtime Database) + Firebase Auth (Google Sign-In).
- **AI**: mai chiamate dirette dal client; tutto passa dal Cloudflare Worker `scuolaboard-groq-proxy` (vedi `worker cloudflare.txt`), che valida il token Firebase e il ruolo `prof`.
- **Hosting**: GitHub Pages serve la cartella **`docs/`** committata su `main`.

## Comandi

```bash
npm run dev          # dev server — DEVE stare su http://localhost:5173
npm test             # vitest run (unit + integrazione)
npm run lint         # eslint
npm run typecheck    # tsc --noEmit (strict: true)
npm run test:e2e     # Playwright (in locale usa il Chrome di sistema)
npm run build        # build di produzione → docs/
npm run format       # prettier
bash scripts/deploy.sh "messaggio commit"
```

- **Porta 5173 obbligatoria**: è l'unica origine in whitelist nel Worker (`ALLOWED_ORIGINS`). Su un'altra porta (es. 5174) tutte le chiamate AI falliscono con `403 Forbidden` "Origine non autorizzata". Usa `npx vite --port 5173 --strictPort`.
- Prima di considerare finito un cambio non banale: `npm run typecheck` + i test pertinenti.

### Il verde non basta: si giudica l'exit code

⚠️ **`vitest run` esce con codice 1 anche quando tutti i test passano**, se durante il run c'è una *unhandled rejection*. Il caso è reale: `fbSave` (`src/app-utils.tsx`) mostra il toast d'errore e poi **restituisce la promise originale, ancora rifiutata**; un chiamante che fa solo `.then()` lascia una promise derivata senza gestore. Successe tre volte di fila, ogni volta nella stessa forma (una `if`/`catch` aggiunta in un call site, gli altri lasciati fuori), e una volta ha tenuto la CI rossa per un commit intero.

Regola pratica:
- **giudica `npm test` sull'exit code**, non sul "Test Files passed". In PowerShell: `$LASTEXITCODE` dopo `npm test`. Uno `0` è l'unico verdetto.
- **ogni `.then()` su una promise che può rigettare va chiuso con `.catch()`**, anche vuoto. Il `.catch(function () {})` NON è un dimenticato: quando `fbSave` (o `cardServices.addAmmonizione`) è già lui a mostrare il toast, il catch serve solo a marcare la promise come gestita e a non duplicare il messaggio. Il commento nel codice deve dirlo, così il catch vuoto non viene "pulito" via.
- Non usare `@typescript-eslint/no-floating-promises` come rete: il codebase è `any` ovunque (`db` arriva da `window.db`), quindi la regola non vedrebbe la gran parte delle catene. Il controllo che funziona è l'exit code.

## Regole non negoziabili

1. **`docs/` non va mai committata a mano.** Il job `deploy-docs` della CI rigenera e pusha `docs/` a ogni push su `main` che supera i controlli (commit `build(docs): rigenerazione automatica da CI [skip ci]`). Se `git status` la mostra modificata in locale: `git checkout -- docs/`.
2. **"Ripubblicare le regole Firestore"**: ogni modifica a `rules firestore.txt` richiede pubblicazione manuale in Firebase Console → Firestore → Rules. Un cambio alle rules senza pubblicazione è un cambio incompleto: segnalalo sempre all'utente.
3. **Privacy (GDPR/AI Act)** — dati di studenti minorenni:
   - I nomi reali non devono mai raggiungere l'AI: la pseudonimizzazione (`Studente 1`, …) avviene client-side e le funzioni protette sono `riassuntiCommentiRun`, `runCardAI`, `runCardQ`. Non aggiungere nuovi invii con nomi.
   - Non loggare né mettere in chiaro nomi reali, email o dati di studenti in console, commit, issue o file di test.
   - Ogni contenuto generato dall'IA deve mostrare il badge `🤖 Supporto IA – revisionato dal docente`.
   - L'IA non assegna voti: i quiz restano bozze da approvare (`aiConfirmaQuiz`).
4. **Segreti**: `migrations/service-account.json`, `.env*`, `*.key`, `*.pem` non vanno mai committati né stampati.
5. **Filtro email**: possono accedere solo `@ferrarisfermiclass.it` e la whitelist docente. Il controllo esiste sia client (`src/auth.ts`) sia server (`isEmailAutorizzata()` nelle rules): se ne tocchi uno, allinea l'altro.
6. **Coverage**: non abbassare le soglie in `vitest.config.js` per far passare un test; se salgono, alzale.
7. **Anni scolastici** (leggere prima di toccarli):
   - `CFG.ANNI_DISPONIBILI` (`src/app-state.ts`) e gli anni enumerati nelle Firestore Rules (`classiPerAnnoSoloAggiunte()`) **devono restare uguali**: lo verifica `src/rules-anni-consistency.test.ts` (test statico che legge i due file). Se ne aggiungi uno, aggiorna entrambi nello stesso commit.
   - `CFG.ANNO_DEFAULT` = anno "ufficiale": è l'**unico** per cui la scelta classe è obbligatoria (`AppProvider` → effect su `annoScolastico`).
   - `ANNO_LEGACY` (`src/app-provider-helpers.ts`) = anno dell'epoca in cui il vecchio sistema scriveva il campo piatto `classe`. **Non** usare `ANNI_DISPONIBILI[0]`.
   - La classe dello studente per un anno si calcola **solo** con `classeCorrenteOf(user, anno, ANNO_LEGACY)` (UI, filtro card, elenco studenti, rinomina classe): niente copie locali della formula.
   - La scelta classe dello studente è **irreversibile** lato rules per un anno già valorizzato: nessun flusso deve poter far scegliere una classe "per sbaglio" (l'anno legacy è l'unica eccezione, via `classe` piatto).

8. **Ordine della griglia** (leggere prima di toccarlo): `compareCards()` in `src/cards.ts` è l'unico punto che lo decide, con questa gerarchia di **priorità**:
   1. **fissate** (`pinned`): sempre davanti a tutte, per TUTTI (campo sul documento Firestore, non locale);
   2. **trascinamento** (`ordine`, drag & drop del prof): quando il prof trascina, i bump si **azzerano** (`clearAperti()` passata a `useDragDrop`) e l'ordine manuale vince;
   3. **apertura recente** (mappa `{ id: timestamp }` per utente in `localStorage: sb_aperti_<uid>`): sale in cima ciò che è stato aperto di recente, sotto il gruppo fissato.
   - La griglia (`GRID_STYLE` in `CardGrid.tsx`) è una **grid row-major** (`repeat(auto-fill, minmax(min(300px, 100%), 1fr))`): così la priorità si legge da sinistra a destra sulla prima riga. **Non** tornare alle colonne CSS (`columns`/masonry): riempiono la prima colonna dall'alto in basso e la priorità finisce impilata in verticale. Le media query di `styles.css` usano `grid-template-columns`, non `columns`.
   - `markAperto()` si chiama **solo** dove una card viene davvero aperta (click su `openCard` e deep-link `?card=`); l'aperti è una preferenza di lettura locale, non va mai su Firestore.
   - `visibleSorted` può cambiare **senza** che cambi `cards`: ogni `useMemo` che lo contiene deve avere la sua identità tra le dipendenze (vedi `cardsValue` in `AppProvider`), altrimenti la griglia resta nell'ordine vecchio.

9. **Il `memo` di `CardItem` confronta una lista esplicita** (leggere prima di toccarlo): `CardItem` riceve l'oggetto `$` e ne legge **42 campi**, ma `memo(…, cardItemAreEqual)` ne confronta solo 14: gli altri sono handler e utility con identità stabile. Il pericolo è **silenzioso**: se leggi `$.qualcosa` nella card e non lo classifichi, la card smette di aggiornarsi quando quel campo cambia — nessun errore, nessun test rosso, solo "la card non reagisce".
   - Ogni `$.campo` letto in `CardItem.tsx` va in **una delle due liste** esportate dal modulo: `CAMPI_CARD_ITEM` (un cambio deve ri-renderizzare la card) o `CAMPI_NON_CONFRONTATI` (handler stabili da `useMemo(…, [])`, oppure utility/format). `src/carditem-memo-campi.test.ts` **fallisce** se compare un `$.campo` non classificato: aggiungere una lettura è un atto consapevole, non una dimenticanza.
   - Non aggiungere a `CAMPI_NON_CONFRONTATI` nulla che non sia stabile per identità: la card chiamerebbe una **chiusura vecchia**. E non aggiungere a `CAMPI_CARD_ITEM` un campo che cambia identità a ogni render: la memo perderebbe senso (è il difetto opposto, cioè la perdita di ottimizzazione).

10. **UI della card in bacheca** (`CardItem.tsx`): a riposo si vedono il chip del **tipo** + al massimo **uno stato** (priorità: fissata → nascosta → nuova). **Eccezione**: il badge `card-avviso` "📣 AVVISO NON INVIATO" (solo docente, annuncio di classe non partito) è **sempre visibile** e non ha `.card-badge-extra`: segnala un problema, non uno stato informativo. La decisione (e il testo con i nomi di chi manca) stanno in `avvisoInSospeso`/`etichettaAvviso`/`dettaglioMancanti` in `avvisi-classe.ts`, non nel componente. Gli altri badge hanno la classe `card-badge-extra` (rivelati dal CSS al passaggio del mouse, sempre visibili su touch) e **devono restare nel DOM**: i test li cercano. Le azioni sono su due righe: primarie (👍 like, 💬 Commenta, ★/✏️, toggle `aria-label="Altre azioni"`) e secondarie dietro il toggle (fissa, riassumi, copia link, modifica del prof, duplica, copia anno, elimina, reazioni). Una azione nuova va nel gruppo secondario, e i test devono **aprire il toggle prima di cliccarla**.

11. **Avvisi di classe / notifiche in-app** (leggere prima di toccarli):
    - Tutta la regola vive in **`src/avvisi-classe.ts`**, ed è l'**unico punto** ammesso: `conAnnuncioInCoda(card)` mette una card in coda d'annuncio, `senzaAnnuncio(card)` la toglie (copie/dupliche: NON sono card nuove per la classe), `annunciaClasse({card, anno, excludeUid})` fa il fan-out e chiude il flag, `avvisiDaRecuperare()` seleziona gli invii interrotti. **Non scrivere `avvisiPendenti`/`avvisiDaMs` a mano** in un altro file: ogni azione nuova che rende visibile una card deve passare da qui, altrimenti non viene annunciata (né recuperata).
    - Il fan-out lo fa il **browser del docente** (non c'è un server): `annunciaClasse` tiene `avvisiPendenti: true` finché l'invio non è concluso, e il flag torna `false` **solo** a fan-out riuscito. Se la scheda si chiude a metà, alla riapertura dell'app un client **docente** ripesca le card ancora pendenti (`avvisiDaRecuperare`: non proposte, non nascoste, anno corrente, entro `AVVISI_RECUPERO_MS` = 72h). Senza il flag le card **non** vengono ri-annunciate (quelle vecchie le ha già annunciate il codice precedente): non togliere il flag né allargare la finestra senza motivo.
    - Le card del docente entrano in coda **al momento della pubblicazione** (`addCard`), non dentro `buildNewCard`: se aggiungi un altro percorso che pubblica qualcosa, chiama `conAnnuncioInCoda` lì.
    - Anche **approvare una proposta** (`appCard`) è una pubblicazione. `avvisiDaMs` serve proprio a questo: la proposta può essere stata creata giorni prima, e senza quell'istante di annuncio il recupero la considererebbe fuori finestra.
    - Gli id delle notifiche di una card sono **deterministici** (`nuova_card_<cardId>`, vedi `notifiche-service.ts`) e `useNotifiche` fa **dedupe per id** in lettura: è così che una riannuncio non produce un doppio avviso. Non tornare a id casuali per `nuova_card`.
    - **Commenti e risposte** (addCom/addReply in `app-handlers.ts`): oltre agli avvisi dedicati (prof, autore del commento parent) fanno il **fan-out alla classe della card** con `tipo: 'risposta'` e `cmId` del nuovo intervento → l'id deterministico diventa `risposta_<cardId>_<cmId>`. Ogni commento è un avviso **distinto**: NON riutilizzare mai `nuova_card_<cardId>` per un commento — collide con l'annuncio della pubblicazione e la dedupe in lettura lo nasconde ai compagni (è stato un bug reale). L'autore del commento è escluso dal fan-out (`excludeUid`). Il **messaggio** porta l'anteprima del testo (`msgConAnteprima` in `app-handlers.ts`, ≤60 caratteri al confine di parola + «…», whitespace unificato): serve a chi riceve a capire se vale l'apertura. In `addCom` il testo va catturato in modo **sincrono** prima di `saveCard`: nel `.then` `ctx.nc` è già svuotato.
    - Un secondo client docente può completare il fan-out di una card pubblicata da un altro: è voluto (chi apre per primo l'app recupera).
    - **Esito e conferma al docente**: `SB.notifyClasse` risolve `{ ok, avvisati }` (`ok: false` = invio non partito o **solo parziale**; non rifiuta mai, i chiamanti storici non hanno `.catch`). `annunciaClasse` condivide **una sola promessa per card e per sessione** (una `Map`, non un flag): recupero e pubblicazione possono partire quasi insieme e chiunque chieda l'annuncio riceve lo stesso esito — senza questo il secondo chiamante riceverebbe 0 e il docente non vedrebbe mai la conferma. `confermaAnnuncio(esito)` traduce l'esito nel toast (`🔔 N studenti avvisati`, oppure l'avviso se non è partito; `null` se non c'è nessuno da avvisare). Il toast lo mostra `mostraEsitoAnnuncio` in `AppProvider` **solo** per pubblicazione e approvazione: il recupero resta silenzioso di proposito. Se un invio non è riuscito il flag NON si chiude, quindi `avvisiPendenti: false` significa davvero "annuncio concluso".
    - **Badge persistente sulla card** (solo docente): finché la coda è aperta il docente vede `card-avviso` con **i nomi di chi non ha ricevuto l'avviso** (`avvisiMancanti: [{ uid, nome }]`, scritto da `annunciaClasse` quando il fan-out è parziale), e può premere **↻ Riprova** → `riprovaAnnuncio` in `AppProvider` chiama `annunciaClasse({ card, forza: true })` (senza `forza` la memoria di sessione restituirebbe il vecchio esito senza riprovare). Quando `avvisiMancanti` c'è, `annunciaClasse` passa `soloUid` a `notifyClasse`: la riprova avvisa **solo quelli**, non tutta la classe (extra, id deterministico → nessun doppione se qualcuno l'aveva già ricevuto). `avvisiMancanti` non è solo un contatore: `mancantiDi()` è la verità per i nomi E per la riprova mirata. ‼️ Contiene nomi di studenti (uid opachi non bastano al docente) e sta in un documento leggibile dagli studenti: è la stessa categoria di dato già presente nei commenti (`autore`), ma se in futuro la si vuole togliere si tenga lì la sola lista di `uid` e si risolvano i nomi lato docente. Se il conteggio non è noto il badge compare dopo `AVVISO_SOSPETTO_MS` (60s): così la pubblicazione normale, che si conclude in un attimo, non fa lampeggiare un falso allarme. Il tempo che passa da solo non fa re-render: se c'è almeno una card pendente parte un battito da 30s (`tickSospesi` in `AppProvider`), spento quando non serve.
    - **Ritentativi automatici**: un annuncio non partito non aspetta la prossima apertura. `creaRitentativiAvvisi` in `avvisi-classe.ts` (controllore senza React, timer iniettabili) tiene per card il tentativo in volo, il ritentativo in programma e i fallimenti consecutivi; le attese sono in `AVVISI_RITENTATIVI_MS` (5s, 15s, 1min, 5min, 15min) e `attesaRitentativo(n)` dice la prossima (`null` = scaletta esaurita: si riprende all'apertura successiva o col pulsante). Un ritentativo **forza** (`forza: true`, altrimenti la memoria di sessione di `annunciaClasse` restituirebbe il vecchio esito senza riprovare) e **rilegge la card** prima di partire: nel frattempo può essere stata nascosta o annunciata altrove. Se riesce dopo un fallimento il docente riceve `confermaRecupero`, altrimenti il badge sparirebbe da solo senza spiegazioni. `Riprova`/`Riprova tutti` usano `{ forza: true, riparti: true }`: azzerano la scaletta, così chi interviene non aspetta l'attesa già cresciuta. `esegui(card)` senza `forza` è idempotente (una sola fan-out per card alla volta), quindi pubblicazione, approvazione e recupero all'apertura possono chiamarla senza duplicare gli invii.
    - **Indicatore in alto** (fascia sticky, solo docente): `annunciInSospeso(cards, now)` elenca le card da riprovare e `etichettaSospesi(n)` ne fa il testo; il pulsante **↻ Riprova tutti** chiama `riprovaTuttiAnnunci`, che rilancia tutte le card con `forza: true` e riporta **un solo** messaggio aggregato (`confermaAnnunci(esiti)`).

12. **Allegati delle card** (leggere prima di toccarli): non esistono tipi TypeScript, sono `any[]` di `{ id, name, type, size, url }` con `url` = **data URL base64 dentro il documento Firestore** (non c'è Storage: `firebase.storage()` è uno shim che restituisce `null`, c'è un test che lo fissa). **Tutto ciò che li riguarda sta in `src/allegati.ts`** ed è una fonte unica: `ESTENSIONI_ALLEGATO`/`TIPI_ALLEGATO_MIME` (allowlist usata da `handleAllegatiUpload`), `ACCETTA_ALLEGATI` (l'attributo `accept` del picker, **derivato** dalla lista: non riscriverlo a mano, è già successo che i due divergessero e le immagini sparissero dal dialog), `MAX_ALLEGATO_KB` (tetto per file, 700KB) e `urlAllegatoSicuro` (allowlist dei protocolli). Il pannelloAllegati della modale è `src/modals/AllegatiPanel.tsx` e mostra quel pannello **solo al docente**: `allegati` è fra i campi vietati allo studente in `rules firestore.txt` (le regole non possono guardare dentro un base64, quindi l'unica difesa possibile è binaria). Il tetto complessivo ~900KB resta in `guardSize` (`AppProvider`) via `CARD_SIZE_LIMIT`.
    - **HTML è ammesso, SVG no**: lo SVG è escluso perché `<img>/<object>/<iframe>` con `data:image/svg+xml` eseguono gli script incorporati. L'HTML non viene mai aperto come documento — un `<a href="data:text/html...">` non aprirebbe nulla (Chrome e Firefox bloccano la navigazione top-level verso `data:` URL): in `CardDetail` la sua riga è un bottone che apre `AllegatoHtmlPreview`, un `iframe` con `sandbox="allow-scripts"` e contenuto in `srcDoc` (`htmlSrcDoc` decodifica la data URL). **`allow-scripts` serve perché i file allegati sono app web, non pagine statiche**: il quiz segnalato dall'utente ha tutte le domande in `.question{display:none}` e le mostra solo con una funzione `init()`; con la sandbox a zero permessi la preview si apriva e restava **vuota** (riprodotto su Chrome e WebKit, non era un problema di iPhone).
    - ‼️ **L'invariante di sicurezza NON è "gli script non girano", è "il file non ha la nostra origine"**: `sandbox="allow-scripts"` **senza** `allow-same-origin` dà origine opaca, quindi l'allegato non può leggere il DOM dell'app, i cookie, `localStorage`, `IndexedDB` né il token Firebase di chi guarda, non può navigare la pagina sopra e non può aprire popup. **Non aggiungere mai `allow-same-origin`** (stored XSS vero) né `allow-top-navigation` / `allow-popups`. È verificato in `e2e/allegati.spec.js` e `e2e/allegati-webkit.spec.js` (che provano a leggere il parent e a scrivere nello storage dell'app dall'interno della iframe). Limite residuo accettato: il file può fare richieste di rete e mostrare grafica a piacere dentro il riquadro; è accettabile perché `allegati` è vietato allo studente e il pannello di caricamento è solo del docente, quindi il file l'ha scritto il prof stesso. Il `download` è l'unico modo per portare il file fuori dal sandbox — **su iOS un `.html` scaricato non si aprirà mai** (iOS non rende i file HTML locali): la preview in-app è l'unico modo per leggerlo sul telefono.
    - **L'URL va sempre passato da un allowlist**: `urlAllegatoSicuro` per gli allegati (http/https/data) e `sbSafeUrl` per i LINK della card (http/https). `href={url}` grezzo è un buco più economico da sfruttare del MIME (basta la stringa `javascript:`) e a cliccarlo sarebbe il **docente** che apre la proposta, con la sessione Firebase in memoria. Per i link il buco era reale: il blocco 🔗 LINK della modale non è gated su `isProf` e `links` non è fra i campi vietati dalle rules, quindi arrivava da una proposta di studente. Un URL respinto non diventa un link: la riga resta inerte con `🔒`. Non fidarsi di nome/MIME (`isHtmlAllegato` guarda anche l'URL per lo stesso motivo: `allegati` non era validato dalle rules).
    - Due invarianti sono congelate da `src/rules-allegati-consistency.test.ts` (test statico sulle rules): `allegati` nei campi vietati della **create** dello studente, e **non** fra quelli dell'`update` (le proposte già esistenti restano votabili/commentabili).

13. **Quiz: badge IA e import da JSON/HTML** (leggere prima di toccarli): le domande stanno in `card.quizDomande`, un array di mappe `{tipo, testo, opzioni[], corretta, hint, ai?}`. **`corretta` cambia significato a seconda del tipo**: per `multipla` è l'INDICE come stringa (`'0'` = prima opzione, 0-based), per `verofalso` è il TESTO (`'Vero'`/`'Falso'`), per `aperta` non c'è. `buildQuizDomande` scarta solo le domande senza testo e le multiple con meno di 2 opzioni: **non valida `corretta`**, quindi una domanda senza risposta giusta arriva in card e viene contata nel quiz senza essere valutabile.
    - **Trasparenza IA (regola 3, non negoziabile)**: `aiConfirmaQuiz` (`ai-services.ts`) è l'**unico punto** in cui contenuto IA entra in una card, ed è lì che mette `ai: true` su ogni domanda. Non spostare il marchio nella UI: si perderebbe copiando o duplicando la card e la conformità evaporerebbe in silenzio. Il badge è il componente `src/BadgeAi.tsx` (testo unico, riusato da `AIPanel`, `QuizPanel` e `QuizBuilder`): se serve altrove, riusa quello e non riscrivere la frase. `QuizPanel` mostra il badge se **almeno una** domanda è IA; `QuizBuilder` colora la card della domanda. Le domande **importate** NON hanno il flag: dichiarare IA il contenuto del docente sarebbe falso, e la PrivacyModal lo promette agli studenti.
    - **Import da file**: `src/quiz-import.ts` è un modulo PURO (niente React/DOM) che legge testo e riconosce tre forme: array nudo, `{domande|questions|quiz:[…]}`, e **HTML con il JSON dentro** (`const quizData = [...]`, il formato dei file .html segnalati dall'utente). Riconosce i campi `question|testo|domanda`, `options|opzioni`, `isCorrect` sull'opzione, `correct|corretta` come indice 0-based (1-based solo se il numero è fuori scala 0-based) o come testo, `hint`, `rationale`. Una domanda senza opzioni diventa `aperta`, due opzioni Vero/Falso diventano `verofalso`. **Non scarta niente in silenzio**: `EsitoImport.scartate` dice indice e motivo, e `QuizBuilder` lo mostra. Un file non valido è un `errore` descrittivo, mai un'eccezione. Non mettere MAI `ai: true` qui. Verificato sul file reale: 12 domande su 12, opzioni e risposte corrette al posto giusto.
    - **La regola di "risposta giusta?" è in `src/quiz-corretta.ts`, non in due posti**: `rispostaGiusta`, `testoRisposta` e `testoCorretta` sono l'unico criterio per punteggio, pannello docente e pannello studente. Era scritta tre volte con tre criteri diversi (`useQuiz` con `String()`, pannello prof con `===` rigido, pannello studente senza il fallback sul testo) e i pannelli si contraddicevano: la docente vedeva **2/6 e tutte le risposte marcate errate**. La ragione dei due confronti: la risposta dello studente è **sempre l'indice** (numero) e `corretta` per `multipla` è l'indice **come stringa**. Se aggiungi un quinto punto che confronta risposte, non duplicare: usa il modulo.
    - **`quizTotale(domande)`** è l'unico denominatore del punteggio (punteggio salvato, testo allo studente, classifica, testata). Contano solo le domande chiuse con una `corretta` valida **e in scala**: un'aperta non conta (il suo giudizio è un riscontro IA, non un voto: regola 3) e una risposta giusta fuori scala nemmeno (nessuno la può azzeccare). Prima ogni punto contava per conto suo e lo studente vedeva `3/4` mentre il docente leggeva `3/3`.
    - **La valutazione IA delle aperte è un RISCONTRO, non un voto**: `valutaAperteProfAI` scrive solo `aiScores` (+`aiErrori`) e **non** tocca `punteggio` (regola 3, e la PrivacyModal lo promette). Tre cose da non ripetere: le chiamate vanno **in serie** (il throttle globale è di 5s e controllato in modo sincrono: emetterne due nello stesso tick fa fallire la seconda e il documento veniva comunque marcato `aiValutato: true`, con il bottone "Riprova" disabilitato e un punteggio non recuperabile); il `voto` va clampato in 0..1 (un `voto: 8` faceva `NaN` e perdeva **tutto** il batch); il prompt è l'unico con testo di studente e va protetto con `escapeForPrompt` + `<USER_DATA>`.
    - `quizTimer` ora **scorre davvero** (`qSecondi` per cardId in `useQuiz`): il tempo che chiama a zero consegna da solo e `tempoUsato` viene salvato. `qInviati` è una mappa per cardId: con il vecchio booleano globale, riaprendo un quiz già consegnato il bottone tornava e il secondo invio (update) veniva negato dalle rules.
    - `src/rules-utils.ts` è il **solo** parser dei test statici sulle Rules (i commenti citano il codice vietato, e in CRLF `\r` è un line terminator: un `\/\/.*$` non abbinava nulla). **Quattro cose che le Rules non perdonano**, tutte congelate da test statici perché il Firestore finto le ignora: su `create` `resource` è `null`, quindi `resource.data` fa scattare l'errore di valutazione e la regola diventa `false` in silenzio (`/notifiche` ha `create` e `update` separati per questo); un campo inesistente sul documento rende una condizione sempre falsa (non esiste `role` sul doc notifiche: il ruolo si legge da `get(/databases/$(database)/documents/users/$(uid))`); `keys()` conta una chiave presente anche se vale `0`; e **una regola va scritta guardando cosa fa il client, non cosa dovrebbe fare**: la prima stesura di `aggiornaNotifica` limitava lo studente al doc del prof e ha spento le notifiche fra studenti in produzione, perché `addCom`/`addReply` notificano anche l'autore della card e l'autore del commento parent, che possono essere studenti (`src/app-handlers.ts`). Lo studente può **accodare una voce** sul doc di chiunque (`lista.hasAll(...)` vieta di togliere voci o riscriverne, `size() <= size()+1` vieta di aggiungerne più di una: `<=` e non `==` perché il fallback del client tiene `.slice(-50)` e a lista piena la dimensione non cresce). I test sono `src/rules-proposta-studente.test.ts` e `src/rules-notifiche-consistency.test.ts`.
    - ⚠️ **Niente `isOwner` per lo studente**: non può modificare una card, perché le Rules glielo vietano (l'update studente ammette solo commenti, like, reazioni, voti, visto, ordine). Il gating esisteva in `CardItem`/`CardDetail` e passava i test solo perché il fake **ignora** le Rules. Non è un caso raro: `appCard` mette `proposta: false`, quindi il proponente diventava `isOwner` della card appena approvata, salvava, la scrittura veniva negata e il toast diceva "Card aggiornata ✓". Le due metà del difetto (il bottone e il toast) vanno tolte **insieme**: `fake-firestore.ts` espone `_failWrites(coll)` per provare che il client non mente quando Firestore nega, e il toast di successo aspetta la promessa.
    - ⚠️ Il fake Firesto **non applica le Rules**: ogni test che verifica una scrittica negata deve passare da `_failWrites`, mai fidandosi del fatto che il fake "ha accettato".
