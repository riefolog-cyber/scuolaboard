# AGENTS.md — Convenzioni per gli agenti su ScuolaBoard

Istruzioni operative per chi (umano o agente) modifica questo repository.
Quando un punto di questo file contraddice `README.md`, vince `README.md`.

## Lingua

- **Rispondi sempre in italiano**, sia nel testo verso l'utente sia nei commenti al codice.
- Messaggi di commit, issue, PR e documentazione sono in italiano (vedi la cronologia: `fix(classi,login): sblocco salvataggio…`).

## Panoramica

ScuolaBoard è una web app per la bacheca digitale scolastica (docenti + studenti):

- **Frontend**: React 18 + TypeScript, bundler **Vite**. `main.tsx` importa i moduli in ordine. Il JSX usa il runtime **automatico** (default di `@vitejs/plugin-react`), in test come in build: lo shorthand `<>` non ha bisogno di importare `React` né `Fragment`. ⚠️ Non reintrodurre `jsxRuntime: 'classic'` con `{ pragma: 'h', pragmaFrag: 'Fragment' }`: era in `vitest.config.js` e non ha mai avuto effetto, perché **Babel rifiuta pragma e pragmaFrag quando il runtime è automatico** ("pragma and pragmaFrag cannot be set when runtime is automatic"). Verificato in tre modi: trasformazione Babel diretta, rimozione di `import { Fragment }` senza rotture, e bundle di produzione che chiama `(0, jsxs)('div', …)`. La guardia `src/no-bare-react.test.ts` resta utile (i moduli legacy usano il global `window.React`), ma non perché il runtime lo richieda.
- **Backend dati**: **Firestore** (non Realtime Database) + Firebase Auth (Google Sign-In).
- **AI**: mai chiamate dirette dal client; tutto passa dal Cloudflare Worker `scuolaboard-groq-proxy` (vedi `worker cloudflare.txt`), che valida il token Firebase e il ruolo `prof`.
- **Hosting**: GitHub Pages serve la cartella **`docs/`** committata su `main`.

## Comandi

```bash
npm run dev          # dev server — DEVE stare su http://localhost:5173
npm test             # vitest run (unit + integrazione)
npm run lint         # eslint
npm run typecheck    # tsc --noEmit (strict: true)
npm run test:e2e     # Playwright (in locale usa il Chrome di sistema)
npm run build        # build di produzione → docs/
npm run format       # prettier
bash scripts/deploy.sh "messaggio commit"
```

- **Porta 5173 obbligatoria**: è l'unica origine in whitelist nel Worker (`ALLOWED_ORIGINS`). Su un'altra porta (es. 5174) tutte le chiamate AI falliscono con `403 Forbidden` "Origine non autorizzata". Usa `npx vite --port 5173 --strictPort`.
- Prima di considerare finito un cambio non banale: `npm run typecheck` + i test pertinenti.

### Il verde non basta: si giudica l'exit code

⚠️ **`vitest run` esce con codice 1 anche quando tutti i test passano**, se durante il run c'è una *unhandled rejection*. Il caso è reale: `fbSave` (`src/app-utils.tsx`) mostra il toast d'errore e poi **restituisce la promise originale, ancora rifiutata**; un chiamante che fa solo `.then()` lascia una promise derivata senza gestore. Successe tre volte di fila, ogni volta nella stessa forma (una `if`/`catch` aggiunta in un call site, gli altri lasciati fuori), e una volta ha tenuto la CI rossa per un commit intero.

Regola pratica:
- **giudica `npm test` sull'exit code**, non sul "Test Files passed". In PowerShell: `$LASTEXITCODE` dopo `npm test`. Uno `0` è l'unico verdetto.
- **ogni `.then()` su una promise che può rigettare va chiuso con `.catch()`**, anche vuoto. Il `.catch(function () {})` NON è un dimenticato: quando `fbSave` (o `cardServices.addAmmonizione`) è già lui a mostrare il toast, il catch serve solo a marcare la promise come gestita e a non duplicare il messaggio. Il commento nel codice deve dirlo, così il catch vuoto non viene "pulito" via.
- Non usare `@typescript-eslint/no-floating-promises` come rete: il codebase è `any` ovunque (`db` arriva da `window.db`), quindi la regola non vedrebbe la gran parte delle catene. Il controllo che funziona è l'exit code.
- `src/test-setup.ts` collega un handler `unhandledRejection` a `src/utils/rejection-guardia.ts`: la rejection viene attribuita al test in corso e l'`afterEach` la trasforma in un errore che **nomina il test** («Unhandled rejection durante «…»: messaggio»), invece di lasciare solo l'exit code 1. L'attribuzione è best-effort (l'evento arriva al termine del turno): le voci che nessun test reclama vengono segnalate a fine file dall'`afterAll`, mai scartate.

## Regole non negoziabili

1. **`docs/` non va mai committata a mano.** Il job `deploy-docs` della CI rigenera e pusha `docs/` a ogni push su `main` che supera i controlli (commit `build(docs): rigenerazione automatica da CI [skip ci]`). Se `git status` la mostra modificata in locale: `git checkout -- docs/`.
   - **Da quel commit nasce un push respinto quasi a ogni volta**: la CI pusha `docs/` mentre il commit locale è ancora in attesa, e `git push` risponde *rejected (fetch first)*. Non è un conflitto: il commit della CI tocca solo `docs/`, il tuo solo `src/`. La procedura è `git pull && git push` (in questo repository `pull.rebase=true`, quindi il pull fa il rebase da solo ed è un fast-forward pulito). **Non** usare `--force`: se i due commit toccassero gli stessi file il rebase si fermerebbe e te lo direbbe, mentre forzare nasconderebbe proprio il caso da vedere.
2. **"Ripubblicare le regole Firestore"**: ogni modifica a `rules firestore.txt` richiede pubblicazione manuale in Firebase Console → Firestore → Rules. Un cambio alle rules senza pubblicazione è un cambio incompleto: segnalalo sempre all'utente.
3. **Privacy (GDPR/AI Act)** — dati di studenti minorenni:
   - I nomi reali non devono mai raggiungere l'AI: la pseudonimizzazione (`Studente 1`, …) avviene client-side e le funzioni protette sono `riassuntiCommentiRun`, `runCardAI`, `runCardQ`. Non aggiungere nuovi invii con nomi.
   - **PII strutturate (email, CF, IBAN, telefoni)**: vivono in `src/utils/pii.ts` e l'unico aggancio è `chiamaAI` (`src/ai-services.ts`), l'unico `fetch` verso il Worker. Non spostare il mascheramento nei call-site: lì copre anche i flussi che non passano da `pseudonimizeComments` (es. `valutaAperteProfAI`) e ogni chiamata futura. Il ripristino va fatto **prima** di `cleanAiMarkdown`/`JSON.parse`. I nomi citati dentro i testi sono coperti da `pseudonimizeComments` (due passate: prima tutti gli autori noti, poi la riscrittura, risposte annidate comprese); i nomi di studenti che non hanno mai commentato restano scoperti (servirebbe il roster). Non tutte le forme sono ovvie: le regole coprono anche **quelle scritte a gruppi** — un IBAN `IT60 X054 2811 0100 0000 1234 56` e un fisso `06 1234 5678` sono la grafia stampata su un estratto conto o un avviso, e senza le loro regole uscivano in chiaro verso il modello (bug reale, corretto). Il limite dichiarato resta il fisso tutto attaccato (`051123456`): allargare la regola a qualunque sequenza di cifre mangerebbe numeri di lezione e date, ed è per questo che il ramo a gruppi chiede 3-4 cifre + separatore + 4 (una data `05/12/2026` non ci arriva).
   - `src/utils/ai-text.test.ts` e `src/utils/pii.test.ts` congelano questi comportamenti: se un test cade, la promessa della PrivacyModal non è più vera.
   - Non loggare né mettere in chiaro nomi reali, email o dati di studenti in console, commit, issue o file di test.
   - Ogni contenuto generato dall'IA deve mostrare il badge `🤖 Supporto IA – revisionato dal docente`.
   - L'IA non assegna voti: i quiz restano bozze da approvare (`aiConfirmaQuiz`).
4. **Segreti**: `migrations/service-account.json`, `.env*`, `*.key`, `*.pem` non vanno mai committati né stampati.
5. **Filtro email**: possono accedere solo `@ferrarisfermiclass.it` e la whitelist docente. Il controllo esiste sia client (`src/auth.ts`) sia server (`isEmailAutorizzata()` nelle rules): se ne tocchi uno, allinea l'altro.
6. **Coverage**: non abbassare le soglie in `vitest.config.js` per far passare un test; se salgono, alzale.
7. **Anni scolastici** (leggere prima di toccarli):
   - `CFG.ANNI_DISPONIBILI` (`src/app-state.ts`) e gli anni enumerati nelle Firestore Rules (`classiPerAnnoSoloAggiunte()`) **devono restare uguali**: lo verifica `src/rules-anni-consistency.test.ts` (test statico che legge i due file). Se ne aggiungi uno, aggiorna entrambi nello stesso commit.
   - `CFG.ANNO_DEFAULT` = anno "ufficiale": è l'**unico** per cui la scelta classe è obbligatoria (`AppProvider` → effect su `annoScolastico`).
   - `ANNO_LEGACY` (`src/app-provider-helpers.ts`) = anno dell'epoca in cui il vecchio sistema scriveva il campo piatto `classe`. **Non** usare `ANNI_DISPONIBILI[0]`.
   - La classe dello studente per un anno si calcola **solo** con `classeCorrenteOf(user, anno, ANNO_LEGACY)` (UI, filtro card, elenco studenti, rinomina classe): niente copie locali della formula.
   - La scelta classe dello studente è **irreversibile** lato rules per un anno già valorizzato: nessun flusso deve poter far scegliere una classe "per sbaglio" (l'anno legacy è l'unica eccezione, via `classe` piatto).

8. **Ordine della griglia** (leggere prima di toccarlo): `compareCards()` in `src/cards.ts` è l'unico punto che lo decide, con questa gerarchia di **priorità**:
   1. **fissate** (`pinned`): sempre davanti a tutte, per TUTTI (campo sul documento Firestore, non locale);
   2. **trascinamento** (`ordine`, drag & drop del prof): quando il prof trascina, i bump si **azzerano** (`clearAperti()` passata a `useDragDrop`) e l'ordine manuale vince;
   3. **apertura recente** (mappa `{ id: timestamp }` per utente in `localStorage: sb_aperti_<uid>`): sale in cima ciò che è stato aperto di recente, sotto il gruppo fissato.
   - La griglia (`GRID_STYLE` in `CardGrid.tsx`) è una **grid row-major** (`repeat(auto-fill, minmax(min(300px, 100%), 1fr))`): così la priorità si legge da sinistra a destra sulla prima riga. **Non** tornare alle colonne CSS (`columns`/masonry): riempiono la prima colonna dall'alto in basso e la priorità finisce impilata in verticale. Le media query di `styles.css` usano `grid-template-columns`, non `columns`.
   - `markAperto()` si chiama **solo** dove una card viene davvero aperta (click su `openCard` e deep-link `?card=`); l'aperti è una preferenza di lettura locale, non va mai su Firestore.
   - `visibleSorted` può cambiare **senza** che cambi `cards`: ogni `useMemo` che lo contiene deve avere la sua identità tra le dipendenze (vedi `cardsValue` in `AppProvider`), altrimenti la griglia resta nell'ordine vecchio.

9. **Il `memo` di `CardItem` confronta una lista esplicita** (leggere prima di toccarlo): `CardItem` riceve l'oggetto `$` e ne legge **42 campi**, ma `memo(…, cardItemAreEqual)` ne confronta solo 14: gli altri sono handler e utility con identità stabile. Il pericolo è **silenzioso**: se leggi `$.qualcosa` nella card e non lo classifichi, la card smette di aggiornarsi quando quel campo cambia — nessun errore, nessun test rosso, solo "la card non reagisce".
   - Ogni `$.campo` letto in `CardItem.tsx` va in **una delle due liste** esportate dal modulo: `CAMPI_CARD_ITEM` (un cambio deve ri-renderizzare la card) o `CAMPI_NON_CONFRONTATI` (handler stabili da `useMemo(…, [])`, oppure utility/format). `src/carditem-memo-campi.test.ts` **fallisce** se compare un `$.campo` non classificato: aggiungere una lettura è un atto consapevole, non una dimenticanza.
   - Non aggiungere a `CAMPI_NON_CONFRONTATI` nulla che non sia stabile per identità: la card chiamerebbe una **chiusura vecchia**. E non aggiungere a `CAMPI_CARD_ITEM` un campo che cambia identità a ogni render: la memo perderebbe senso (è il difetto opposto, cioè la perdita di ottimizzazione).

10. **UI della card in bacheca** (`CardItem.tsx`): a riposo si vedono il chip del **tipo** + al massimo **uno stato** (priorità: fissata → nascosta → nuova). **Eccezione**: il badge `card-avviso` "📣 AVVISO NON INVIATO" (solo docente, annuncio di classe non partito) è **sempre visibile** e non ha `.card-badge-extra`: segnala un problema, non uno stato informativo. La decisione (e il testo con i nomi di chi manca) stanno in `avvisoInSospeso`/`etichettaAvviso`/`dettaglioMancanti` in `avvisi-classe.ts`, non nel componente. Gli altri badge hanno la classe `card-badge-extra` (rivelati dal CSS al passaggio del mouse, sempre visibili su touch) e **devono restare nel DOM**: i test li cercano. Le azioni sono su due righe: primarie (👍 like, 💬 Commenta, ★/✏️, toggle `aria-label="Altre azioni"`) e secondarie dietro il toggle (fissa, riassumi, copia link, modifica del prof, duplica, copia anno, elimina, reazioni). Una azione nuova va nel gruppo secondario, e i test devono **aprire il toggle prima di cliccarla**.

11. **Avvisi di classe / notifiche in-app** (leggere prima di toccarli):
    - Tutta la regola vive in **`src/avvisi-classe.ts`**, ed è l'**unico punto** ammesso: `conAnnuncioInCoda(card)` mette una card in coda d'annuncio, `senzaAnnuncio(card)` la toglie (copie/dupliche: NON sono card nuove per la classe), `annunciaClasse({card, anno, excludeUid})` fa il fan-out e chiude il flag, `avvisiDaRecuperare()` seleziona gli invii interrotti. **Non scrivere `avvisiPendenti`/`avvisiDaMs` a mano** in un altro file: ogni azione nuova che rende visibile una card deve passare da qui, altrimenti non viene annunciata (né recuperata).
    - Il fan-out lo fa il **browser del docente** (non c'è un server): `annunciaClasse` tiene `avvisiPendenti: true` finché l'invio non è concluso, e il flag torna `false` **solo** a fan-out riuscito. Se la scheda si chiude a metà, alla riapertura dell'app un client **docente** ripesca le card ancora pendenti (`avvisiDaRecuperare`: non proposte, non nascoste, anno corrente, entro `AVVISI_RECUPERO_MS` = 72h). Senza il flag le card **non** vengono ri-annunciate (quelle vecchie le ha già annunciate il codice precedente): non togliere il flag né allargare la finestra senza motivo.
    - Le card del docente entrano in coda **al momento della pubblicazione** (`addCard`), non dentro `buildNewCard`: se aggiungi un altro percorso che pubblica qualcosa, chiama `conAnnuncioInCoda` lì.
    - Anche **approvare una proposta** (`appCard`) è una pubblicazione. `avvisiDaMs` serve proprio a questo: la proposta può essere stata creata giorni prima, e senza quell'istante di annuncio il recupero la considererebbe fuori finestra.
    - Gli id delle notifiche di una card sono **deterministici** (`nuova_card_<cardId>`, vedi `notifiche-service.ts`) e `useNotifiche` fa **dedupe per id** in lettura: è così che una riannuncio non produce un doppio avviso. Non tornare a id casuali per `nuova_card`.
    - **Commenti e risposte** (addCom/addReply in `app-handlers.ts`): oltre agli avvisi dedicati (prof, autore del commento parent) fanno il **fan-out alla classe della card** con `tipo: 'risposta'` e `cmId` del nuovo intervento → l'id deterministico diventa `risposta_<cardId>_<cmId>`. Ogni commento è un avviso **distinto**: NON riutilizzare mai `nuova_card_<cardId>` per un commento — collide con l'annuncio della pubblicazione e la dedupe in lettura lo nasconde ai compagni (è stato un bug reale). L'autore del commento è escluso dal fan-out (`excludeUid`). Il **messaggio** porta l'anteprima del testo (`msgConAnteprima` in `app-handlers.ts`, ≤60 caratteri al confine di parola + «…», whitespace unificato): serve a chi riceve a capire se vale l'apertura. In `addCom` il testo va catturato in modo **sincrono** prima di `saveCard`: nel `.then` `ctx.nc` è già svuotato.
    - Un secondo client docente può completare il fan-out di una card pubblicata da un altro: è voluto (chi apre per primo l'app recupera).
    - **Esito e conferma al docente**: `SB.notifyClasse` risolve `{ ok, avvisati }` (`ok: false` = invio non partito o **solo parziale**; non rifiuta mai, i chiamanti storici non hanno `.catch`). `annunciaClasse` condivide **una sola promessa per card e per sessione** (una `Map`, non un flag): recupero e pubblicazione possono partire quasi insieme e chiunque chieda l'annuncio riceve lo stesso esito — senza questo il secondo chiamante riceverebbe 0 e il docente non vedrebbe mai la conferma. `confermaAnnuncio(esito)` traduce l'esito nel toast (`🔔 N studenti avvisati`, oppure l'avviso se non è partito; `null` se non c'è nessuno da avvisare). Il toast lo mostra `mostraEsitoAnnuncio` in `AppProvider` **solo** per pubblicazione e approvazione: il recupero resta silenzioso di proposito. Se un invio non è riuscito il flag NON si chiude, quindi `avvisiPendenti: false` significa davvero "annuncio concluso".
    - **Badge persistente sulla card** (solo docente): finché la coda è aperta il docente vede `card-avviso` con **i nomi di chi non ha ricevuto l'avviso** (`avvisiMancanti: [{ uid, nome }]`, scritto da `annunciaClasse` quando il fan-out è parziale), e può premere **↻ Riprova** → `riprovaAnnuncio` in `AppProvider` chiama `annunciaClasse({ card, forza: true })` (senza `forza` la memoria di sessione restituirebbe il vecchio esito senza riprovare). Quando `avvisiMancanti` c'è, `annunciaClasse` passa `soloUid` a `notifyClasse`: la riprova avvisa **solo quelli**, non tutta la classe (extra, id deterministico → nessun doppione se qualcuno l'aveva già ricevuto). `avvisiMancanti` non è solo un contatore: `mancantiDi()` è la verità per i nomi E per la riprova mirata. ‼️ Contiene nomi di studenti (uid opachi non bastano al docente) e sta in un documento leggibile dagli studenti: è la stessa categoria di dato già presente nei commenti (`autore`), ma se in futuro la si vuole togliere si tenga lì la sola lista di `uid` e si risolvano i nomi lato docente. Se il conteggio non è noto il badge compare dopo `AVVISO_SOSPETTO_MS` (60s): così la pubblicazione normale, che si conclude in un attimo, non fa lampeggiare un falso allarme. Il tempo che passa da solo non fa re-render: se c'è almeno una card pendente parte un battito da 30s (`tickSospesi` in `AppProvider`), spento quando non serve.
    - **Ritentativi automatici**: un annuncio non partito non aspetta la prossima apertura. `creaRitentativiAvvisi` in `avvisi-classe.ts` (controllore senza React, timer iniettabili) tiene per card il tentativo in volo, il ritentativo in programma e i fallimenti consecutivi; le attese sono in `AVVISI_RITENTATIVI_MS` (5s, 15s, 1min, 5min, 15min) e `attesaRitentativo(n)` dice la prossima (`null` = scaletta esaurita: si riprende all'apertura successiva o col pulsante). Un ritentativo **forza** (`forza: true`, altrimenti la memoria di sessione di `annunciaClasse` restituirebbe il vecchio esito senza riprovare) e **rilegge la card** prima di partire: nel frattempo può essere stata nascosta o annunciata altrove. Se riesce dopo un fallimento il docente riceve `confermaRecupero`, altrimenti il badge sparirebbe da solo senza spiegazioni. `Riprova`/`Riprova tutti` usano `{ forza: true, riparti: true }`: azzerano la scaletta, così chi interviene non aspetta l'attesa già cresciuta. `esegui(card)` senza `forza` è idempotente (una sola fan-out per card alla volta), quindi pubblicazione, approvazione e recupero all'apertura possono chiamarla senza duplicare gli invii.
    - **Indicatore in alto** (fascia sticky, solo docente): `annunciInSospeso(cards, now)` elenca le card da riprovare e `etichettaSospesi(n)` ne fa il testo; il pulsante **↻ Riprova tutti** chiama `riprovaTuttiAnnunci`, che rilancia tutte le card con `forza: true` e riporta **un solo** messaggio aggregato (`confermaAnnunci(esiti)`).

12. **Allegati delle card** (leggere prima di toccarli): non esistono tipi TypeScript, sono `any[]` di `{ id, name, type, size }` **nel documento della card**; il CONTENUTO (`url` = data URL base64) vive in `cards/{cardId}/allegati/{fileId}`, **un documento per file** (`src/allegati-card-servizio.ts`, unico punto che parla con la sottocollezione). Motivo: un documento Firestore è limitato a 1 MiB e copertina + due PDF lo superavano ("Card troppo grande (961KB)", caso reale); con un documento per file ogni allegato ha il suo MiB. Non c'è Storage (`firebase.storage()` è uno shim che restituisce `null`, c'è un test che lo fissa). `salvaAllegati` scrive i file e restituisce i metadati; `addCard` scrive **prima** i file e poi la card, e se i file non si scrivono **la card non si salva** (una card che elenca file inesistenti è peggio di un errore). Duplicare/copiare in un altro anno **copia i file** (la copia è indipendente); eliminare una card li cancella (`eliminaTuttiAllegati`: Firestore non fa cascade). Le card vecchie hanno `url` inline: `CardDetail` usa quello se c'è, altrimenti legge la sottocollezione all'apertura (una sola query), quindi **nessuna migrazione forzata** — la migrazione avviene da sola quando il docente modifica la card. **Tutto ciò che riguarda formati e presentazione sta in `src/allegati.ts`** ed è una fonte unica: `ESTENSIONI_ALLEGATO`/`TIPI_ALLEGATO_MIME` (allowlist usata da `handleAllegatiUpload`), `ACCETTA_ALLEGATI` (l'attributo `accept` del picker, **derivato** dalla lista: non riscriverlo a mano, è già successo che i due divergessero e le immagini sparissero dal dialog), `MAX_ALLEGATO_KB` (tetto per file, 700KB) e `urlAllegatoSicuro` (allowlist dei protocolli). Il pannelloAllegati della modale è `src/modals/AllegatiPanel.tsx` e mostra quel pannello **solo al docente**: `allegati` è fra i campi vietati allo studente in `rules firestore.txt` (le regole non possono guardare dentro un base64, quindi l'unica difesa possibile è binaria). Il tetto ~900KB di `guardSize` (`AppProvider`, via `CARD_SIZE_LIMIT`) ora riguarda **solo testo e immagini**: gli allegati non devono tornare dentro `imgUsageKB`/`computeImageTargetKB`, era ciò che costringeva la copertina a essere più piccola del necessario.
    - **Rules della sottocollezione**: `match /allegati/{fileId}` annidato dentro `match /cards/{cardId}` — lettura con la stessa visibilità della card (`get()` sul padre: gli id delle card sono timestamp, quindi indovinabili), scrittura solo docente, campi `hasOnly(['name','type','size','url'])` e `url.matches('^data:.*')`. I campi del servizio (`CAMPI_ALLEGATO`) e quelli delle rules devono restare identici: lo verifica `src/rules-allegati-card-consistency.test.ts`. **Vanno pubblicate a mano in Firebase Console**: un cambio alle rules senza pubblicazione è un cambio incompleto.
    - **HTML è ammesso, SVG no**: lo SVG è escluso perché `<img>/<object>/<iframe>` con `data:image/svg+xml` eseguono gli script incorporati. L'HTML non viene mai aperto come documento — un `<a href="data:text/html...">` non aprirebbe nulla (Chrome e Firefox bloccano la navigazione top-level verso `data:` URL): in `CardDetail` la sua riga è un bottone che apre `AllegatoHtmlPreview`, un `iframe` con `sandbox="allow-scripts"` e contenuto in `srcDoc` (`htmlSrcDoc` decodifica la data URL). **`allow-scripts` serve perché i file allegati sono app web, non pagine statiche**: il quiz segnalato dall'utente ha tutte le domande in `.question{display:none}` e le mostra solo con una funzione `init()`; con la sandbox a zero permessi la preview si apriva e restava **vuota** (riprodotto su Chrome e WebKit, non era un problema di iPhone).
    - ‼️ **L'invariante di sicurezza NON è "gli script non girano", è "il file non ha la nostra origine"**: `sandbox="allow-scripts"` **senza** `allow-same-origin` dà origine opaca, quindi l'allegato non può leggere il DOM dell'app, i cookie, `localStorage`, `IndexedDB` né il token Firebase di chi guarda, non può navigare la pagina sopra e non può aprire popup. **Non aggiungere mai `allow-same-origin`** (stored XSS vero) né `allow-top-navigation` / `allow-popups`. È verificato in `e2e/allegati.spec.js` e `e2e/allegati-webkit.spec.js` (che provano a leggere il parent e a scrivere nello storage dell'app dall'interno della iframe). Limite residuo accettato: il file può fare richieste di rete e mostrare grafica a piacere dentro il riquadro; è accettabile perché `allegati` è vietato allo studente e il pannello di caricamento è solo del docente, quindi il file l'ha scritto il prof stesso. Il `download` è l'unico modo per portare il file fuori dal sandbox — **su iOS un `.html` scaricato non si aprirà mai** (iOS non rende i file HTML locali): la preview in-app è l'unico modo per leggerlo sul telefono.
    - **L'URL va sempre passato da un allowlist**: `urlAllegatoSicuro` per gli allegati (http/https/data) e `sbSafeUrl` per i LINK della card (http/https). `href={url}` grezzo è un buco più economico da sfruttare del MIME (basta la stringa `javascript:`) e a cliccarlo sarebbe il **docente** che apre la proposta, con la sessione Firebase in memoria. Per i link il buco era reale: il blocco 🔗 LINK della modale non è gated su `isProf` e `links` non è fra i campi vietati dalle rules, quindi arrivava da una proposta di studente. Un URL respinto non diventa un link: la riga resta inerte con `🔒`. Non fidarsi di nome/MIME (`isHtmlAllegato` guarda anche l'URL per lo stesso motivo: `allegati` non era validato dalle rules).
    - Due invarianti sono congelate da `src/rules-allegati-consistency.test.ts` (test statico sulle rules): `allegati` nei campi vietati della **create** dello studente, e **non** fra quelli dell'`update` (le proposte già esistenti restano votabili/commentabili). La sottocollezione ha il suo test statico in `src/rules-allegati-card-consistency.test.ts` (campi ammessi = `CAMPI_ALLEGATO`, lettura legata alla visibilità del padre, create/update separati).

13. **Quiz: badge IA e import da JSON/HTML** (leggere prima di toccarli): le domande stanno in `card.quizDomande`, un array di mappe `{tipo, testo, opzioni[], corretta, hint, ai?}`. **`corretta` cambia significato a seconda del tipo**: per `multipla` è l'INDICE come stringa (`'0'` = prima opzione, 0-based), per `verofalso` è il TESTO (`'Vero'`/`'Falso'`), per `aperta` non c'è. `buildQuizDomande` scarta solo le domande senza testo e le multiple con meno di 2 opzioni: **non valida `corretta`**, quindi una domanda senza risposta giusta può arrivare in card dalla modifica a mano — non viene cancellata (il docente l'ha scritta) ma **non entra nel denominatore**, perché sarebbe un punto perso per tutti (vedi `quizTotale`). L'unico ingresso automatico, l'import, non ne crea più: una domanda senza risposta dichiarata viene scartata lì.

Non spostare il marchio nella UI: si perderebbe copiando o duplicando la card e la conformità evaporerebbe in silenzio. Una domanda senza opzioni diventa `aperta`; due opzioni Vero/Falso diventano `verofalso` **solo se la risposta è dichiarata**, altrimenti si scarta con il motivo: prima il ramo vero/falso sceglieva la PRIMA opzione, quindi `correct: false` — che finiva in `String(false)` = `"false"`, testo di nessuna opzione — salvava `corretta: "Vero"`, cioè l'opposto del file, e chi rispondeva giusto risultava sbagliato. **Non scarta niente in silenzio**: `EsitoImport.scartate` dice indice e motivo, e `QuizBuilder` lo mostra. Un file non valido è un `errore` descrittivo, mai un'eccezione. Non mettere MAI `ai: true` qui. Verificato sul file reale: 12 domande su 12, opzioni e risposte corrette al posto giusto.
    - **La regola di "risposta giusta?" è in `src/quiz-corretta.ts`, non in due posti**: `rispostaGiusta`, `testoRisposta` e `testoCorretta` sono l'unico criterio per punteggio, pannello docente e pannello studente. Era scritta tre volte con tre criteri diversi (`useQuiz` con `String()`, pannello prof con `===` rigido, pannello studente senza il fallback sul testo) e i pannelli si contraddicevano: la docente vedeva **2/6 e tutte le risposte marcate errate**. La ragione dei due confronti: la risposta dello studente è **sempre l'indice** (numero) e `corretta` per `multipla` è l'indice **come stringa**. Se aggiungi un quinto punto che confronta risposte, non duplicare: usa il modulo.

Conta una domanda chiusa **solo se qualcuno può rispondere giusto**: non le aperte (il loro giudizio è un riscontro IA, non un voto: regola 3), non quelle senza risposta dichiarata, e nemmeno quelle la cui `corretta` non è raggiungibile da un click (indice fuori scala, oppure un testo che non è fra le opzioni — es. `verofalso` con `corretta: "Vero"` su opzioni `["Giusto","Sbagliato"]`). Resta vero anche il difetto storico del conteggio: ogni punto contava per conto suo e lo studente vedeva `3/4` mentre il docente leggeva `3/3`.

Tre cose da non ripetere: le chiamate vanno **in serie** (il throttle globale è di 5s e controllato in modo sincrono: emetterne due nello stesso tick fa fallire la seconda) e ognuna attende il resto della finestra con `SB.attesaAI` (`attesaProssimaAI` in `src/ai-services.ts`, calcolata da `ai-throttle.ts`) **prima** di partire: prima c'erano 5.100 ms fissi e solo fra le domande dello stesso studente, quindi la prima domanda del secondo partiva subito dopo l'ultima del primo e veniva rifiutata, segnando quello studente come non valutato; il `voto` va clampato in 0..1 (un `voto: 8` faceva `NaN` e perdeva **tutto** il batch); il prompt è l'unico con testo di studente e va protetto con `escapeForPrompt` + `<USER_DATA>`.
    - `quizTimer` ora **scorre davvero** (`qSecondi` per cardId in `useQuiz`): il tempo che chiama a zero consegna da solo e `tempoUsato` viene salvato. `qInviati` è una mappa per cardId: con il vecchio booleano globale, riaprendo un quiz già consegnato il bottone tornava e il secondo invio (update) veniva negato dalle rules.
    - `src/rules-utils.ts` è il **solo** parser dei test statici sulle Rules (i commenti citano il codice vietato, e in CRLF `\r` è un line terminator: un `\/\/.*$` non abbinava nulla). **Quattro cose che le Rules non perdonano**, tutte congelate da test statici perché il Firestore finto le ignora: su `create` `resource` è `null`, quindi `resource.data` fa scattare l'errore di valutazione e la regola diventa `false` in silenzio (`/notifiche` ha `create` e `update` separati per questo); un campo inesistente sul documento rende una condizione sempre falsa (non esiste `role` sul doc notifiche: il ruolo si legge da `get(/databases/$(database)/documents/users/$(uid))`); `keys()` conta una chiave presente anche se vale `0`; e **una regola va scritta guardando cosa fa il client, non cosa dovrebbe fare**: la prima stesura di `aggiornaNotifica` limitava lo studente al doc del prof e ha spento le notifiche fra studenti in produzione, perché `addCom`/`addReply` notificano anche l'autore della card e l'autore del commento parent, che possono essere studenti (`src/app-handlers.ts`). Lo studente può **accodare una voce** sul doc di chiunque (`lista.hasAll(...)` vieta di togliere voci o riscriverne, `size() <= size()+1` vieta di aggiungerne più di una: `<=` e non `==` perché il fallback del client tiene `.slice(-50)` e a lista piena la dimensione non cresce). I test sono `src/rules-proposta-studente.test.ts` e `src/rules-notifiche-consistency.test.ts`.

Il gating esisteva in `CardItem`/`CardDetail` e passava i test solo perché il fake **ignora** le Rules. Non è un caso raro: `appCard` mette `proposta: false`, quindi il proponente diventava `isOwner` della card appena approvata, salvava, la scrittura veniva negata e il toast diceva "Card aggiornata ✓". Le due metà del difetto (il bottone e il toast) vanno tolte **insieme**: `fake-firestore.ts` espone `_failWrites(coll)` per provare che il client non mente quando Firestore nega, e il toast di successo aspetta la promessa.

Ora `esitoOttimistico` chiude la catena (risolve `true`/`false`, **non** rigetta: i gestori di click non hanno un `.catch`) e il toast parte solo in `.then`. `eseguiRinomina` marca come gestita la promise di ogni `fbSave`: un `try/catch` sincrono non prende una rejection, e ogni card non salvata restava una unhandled rejection che faceva uscire `vitest` con 1.

14. **Un errore non cancella dati già mostrati** (leggere prima di toccare `firestore-sync.ts`): l'handler di errore di `onSnapshot` **conserva l'ultimo snapshot valido**. Prima faceva `snapshot = []`, e la conseguenza era che un QUALSIASI errore transitorio — segnale perso, cambio di rete, WebSocket chiusa — faceva comparire "Nessun contenuto visibile" al posto delle card: un'affermazione falsa, perché le card non erano sparite, erano illeggibili *in quel momento*. Verificato sul telefono: era questo il difetto, non la cache persistente.
    - **Non "ottimizzare" azzerando lo snapshot per risparmiare memoria**: meglio card un po' datate che nessuna card. Se invece non è mai arrivato nulla, lo stato vuoto è corretto e l'utente va avvisato (una volta per episodio, identificato per **codice** d'errore, non per identità dell'oggetto `Error`, che è nuovo a ogni oscillazione).
    - Le trappole inverse sono già coperte: il toast di successo deve **aspettare la promessa** (vedi regola 13), e il testo scritto dall'utente non si azzera se la scrittura fallisce.
    - **Il mapping dello snapshot riusa l'oggetto della card quando il documento non è cambiato** (`aggiornaMappaDaSnapshot`: `docChanges` → `applicaDocChanges`, con fallback per gli snapshot che non lo espongono). `CardItem` è memoizzato con `prev.c !== next.c`: se il mapping ricrea tutti gli oggetti — com'era `s.forEach(d => a.push(d.data()))` — un solo like ri-renderizza **tutte** le card e il memo a 14 campi diventa inerte. `src/firestore-sync-memo.test.ts` lo fissa (30 card, un documento cambiato ⇒ **una** identità nuova) e il Profiler misura 60 card: ~273 ms con oggetti tutti nuovi contro ~9 ms con uno nuovo. Non tornare al mapping completo "per semplicità": la semplificazione costa 30× sul render.
    - `fake-firestore.ts` espone `_failReads(coll)`/`_allowReads(coll)` per simulare la caduta della connessione (`_failReads` notifica subito i listener, come farebbe Firestore). I test di questa regola stanno in `src/integration/regression-fixes.test.tsx` e **non devono usare attese a tempo fisso**: su runner caricato falliscono (è il flake già noto, vedi `perf-profiler.test.tsx`). Aspetta una condizione positiva con `waitFor`.

15. **Toast e undo delle eliminazioni** (leggere prima di toccarli): i toast nascono da DUE punti — il hook `src/hooks/useToast.ts` (messaggi normali) e `AppProvider` (il toast «Card eliminata» con undo) — e la regola comune sta in **`src/utils/toast.ts`**, non nei chiamanti.
    - **Id da `nuovoIdToast()`, mai `Date.now()`**: due toast nello stesso millisecondo avevano lo stesso id, React segnalava chiavi duplicate e la chiusura di uno (la rimozione è per id) portava via anche l'altro.
    - **Tetto a `MAX_TOAST` nell'accodamento** (`aggiungiToast`), non nel render: il vecchio `slice(-5)` in `Toasts.tsx` tagliava solo ciò che si vedeva, l'array cresceva e un toast con «↩ Annulla» poteva sparire dallo schermo restando in sospeso. Si scarta prima un toast informativo, e **un toast annullabile non si scarta mai**: con più di MAX eliminazioni in sospeso insieme non c'è niente da buttare senza perdere un'azione, quindi la lista supera MAX (ogni voce muore comunque entro i 5s dell'undo). **Il toast appena accodato non è mai un candidato**: era il caso limite in cui un messaggio appena mostrato sarebbe sparito subito, e chi lo aveva chiesto avrebbe creduto di averlo visto.
    - **La ✕ c'è su ogni toast che può RESTARE**, non su quelli con `undo` (`aria-label="Chiudi notifica"` → `chiudiToast(id)` dal contesto): con `TOAST_TIMEOUT_MS = 0` nessun timer chiude un toast informativo, e senza un comando resterebbe sullo schermo per tutta la sessione (WCAG 2.2.1). Non toglierla "perché tanto c'è il timer": quel timer è configurabile e può essere spento. Il toast con undo invece lo chiude **sempre** il suo controllore dopo `UNDO_ELIMINAZIONE_MS`, quindi non ne ha bisogno e non deve averla: chiuderlo senza annullare lascerebbe partire la cancellazione della card senza più poterla revocare, e chiuderlo annullando direbbe il contrario di quello che fa la ✕ altrove. La sua unica uscita è «↩ Annulla». Se una chiamata diretta chiude comunque un toast con undo in sospeso, `chiudiToast` in `AppProvider` **annulla** quell'eliminazione (la card resta) invece di lasciarla partire in silenzio.
    - **La chiusura passa da un solo punto**: `chiudiToast` del hook (`src/hooks/useToast.ts`) ferma anche il timer di auto-chiusura; un `setToasts(function (p) { return p.filter(...) })` scritto a mano in un altro file lascia il timer in volo, e allo smontaggio dell'app aggiorna lo stato di un componente che non c'è più. Il hook tiene i timer in una `Map` in un `ref` e la svuota nello smontaggio; `src/useToast.test.tsx` lo fissa contando i timer (`vi.getTimerCount()`).
    - **L'undo è per toast, non globale**: `src/undo-eliminazione.ts` (`creaUndoEliminazioni`, controllore senza React con timer iniettabili) tiene una voce per `toastId`; il pulsante passa `t.id` e annulla la SUA card. Con un solo stato in sospeso il pulsante del primo toast annullava la seconda card e la prima veniva cancellata comunque. Non tornare a `undoDelete` come stato operativo: il campo resta nel contesto solo per compatibilità.
    - **Una card, una sola eliminazione in sospeso**: `avvia` rifiuta una seconda voce per la stessa card (confronto per id) e `delCardWithUndo` rispetta il `false` senza accodare il toast. Il doppio clic su «Elimina» (o il doppio tocco sul telefono) creava due toast identici: il primo timer cancellava la card e l'«↩ Annulla» del secondo, arrivando dopo, rispondeva «Eliminazione annullata ✓» per una card già sparita — un messaggio falso.
    - **Il toast dice QUALE card**: il messaggio è `Card eliminata: <titolo>` (titolo da `anteprimaTesto`, ≤60 caratteri al confine di parola) e non il generico «Card eliminata». Con due eliminazioni ravvicinate i messaggi erano identici e l'unico modo per capire quale «↩ Annulla» premere era la posizione.
    - **La cancellazione non può lasciare un toast orfano**: se `elimina` solleva (guasto sincrono, es. `db` non inizializzato — `fbDel` non rigetta mai, quindi una rejection non arriva qui), il timer chiude comunque il toast e segnala l'errore con il canale `errore` (in `AppProvider`: «Non riesco a eliminare la card»). Senza il `finally` un'eccezione uscita dal timer lascerebbe sullo schermo un toast con undo, che non ha la ✕, per sempre.
    - **`TOAST_TIMEOUT_MS` (`src/app-state.ts`) è l'unica fonte della durata**: `0` = persistente (nessun timer), valori invalidi (`NaN`, `Infinity`, negativi) tornano a 2400. `src/useToast.test.tsx` e `src/utils/toast.test.ts` congelano queste regole; `src/undo-eliminazione.test.ts` congela l'indipendenza delle eliminazioni.


16. **Visibilità per classe: un criterio solo** (leggere prima di filtrare le card per classe):
    - `visibileAClasse(card, classe)` in `src/card-classi.ts` è l'**unica** risposta a "questo studente vede questa card?". Conosce le tre cose che un `classi.indexOf` non conosce: il segnaposto `TUTTE` (card per tutti, presente in `classi` e non in ogni lista), le **esclusioni** (`classiEscluse: ['3A']`, la card tolta a quella classe) e le card legacy senza `classi` (valgono per tutti). `classi: []` = solo docente. `classiDi` scarta le voci non-stringa o vuote (`['3A', null]`): un array sporco faceva stampare «3A, » e con sole voci invalide l'etichetta restava VUOTA mentre la card non era visibile a nessuno.
    - Non riscrivere il criterio: è successo tre volte in un solo giro di review (cloud del docente, analisi AI per classe e "suddivisa") e ogni volta sbagliava in silenzio — una card per TUTTE spariva da ogni classe, una card tolta alla 3A continuava a contare come 3A. `src/classi-criterio.test.ts` fallisce se ricompare `(x.classi || []).indexOf/includes`; per un confronto con un nome **letterale** (la rinomina) si dichiara il perché nel codice.
    - **Anche LEGGERE il campo passa da `classiDi`**, non solo decidere: la ricerca (`CercaModal`), i chip di card e dettaglio, i prompt AI, la copia di una proposta e il fan-out delle notifiche leggevano `c.classi || ['TUTTE']` per conto loro. Non è un criterio, quindi la prima guardia non lo vedeva, ma è la stessa regola copiata: con `classi: ['3A', null]` il chip stampava «3A, » e una card legacy senza `classi` compariva nella ricerca come «Solo prof» (il contrario di quel che è). `src/classi-criterio.test.ts` ora fallisce anche su `.classi ||` fuori da `card-classi.ts`, con due eccezioni dichiarate: `NuovaCardModal` e `AppProvider` leggono lo stato del **form**, non una card.
    - Il **word cloud di una classe** filtra anche i commenti con `commentiVisibili` (`commenti-classe.ts`): i commenti sono discussioni di classe, e il cloud della 3A non deve contenere quello scritto dalla 3B sulla stessa card.
    - **L'etichetta della destinazione esce dallo stesso modulo** (`etichettaClassi`): vista elenco, dettaglio e foglio stampato la calcolavano ognuno per conto suo e **nessuno** leggeva `classiEscluse` — una card «tolta alla 3A» si presentava come «Tutte le classi» proprio al docente che l'aveva tolta, e la stampa mostrava il segnaposto `TUTTE` (o, nella vista «solo prof», perfino l'identificatore interno `_solo` su un foglio che finisce in mano agli studenti). Il **chip** di card e dettaglio usa la forma breve `etichettaEsclusioni` («tranne 3A»): la frase intera in un badge non ci sta, e senza un chip la card tolta a una classe si presenta come «per tutti» proprio dove il docente decide.
    - **Una scrittura non contiene contraddizioni**: `escluseCoerenti` toglie dalle esclusioni la classe elencata **esplicitamente** in `classi` (vince l'elenco; `TUTTE` non è un elenco, quindi le esclusioni restano valide), e l'editor toglie l'esclusione appena si seleziona quella classe. Senza, scegliere solo la 3A su una card «tutte tranne 3A» salvava entrambe le cose e `visibileAClasse` faceva vincere l'esclusione: la card spariva a tutti gli studenti, nessun errore e nessuna schermata che lo dicesse. Scrivere il gesto «togli da questa classe» è `senzaClasse` (`card-classi.ts`), e fa **una cosa sola**: classe esplicita → esce da `classi`; `TUTTE` → entra in `classiEscluse`. `togliDaClasse` non deve tornare ad aggiungere sempre l'esclusione: il documento direbbe «3A, 4B tranne 3A» e l'editor, risalvando, la toglierebbe.
    - La coerenza va rifatta a **ogni** scrittura, non solo nell'editor: `senzaClasse` sul ramo esplicito riallinea le esclusioni residue con `escluseCoerenti`. Un documento scritto dalla versione precedente può avere `classiEscluse: ['3A']` accanto a `classi: ['3A','4B']`, e togliendo la 4B resterebbe «3A tranne 3A»: la card non la vedrebbe più nessuno studente, senza errore e senza che una schermata lo dica.
    - **Rinominare una classe** (`eseguiRinomina`) riscrive `classi` **e** `classiEscluse`: un'esclusione rimasta col vecchio nome torna a valere per gli stessi studenti col nome nuovo (e una futura classe omonima la erediterebbe). Stessa logica di `classiPerAnno` degli studenti. Lo stesso vale per i **commenti** (`rinominaClasseCommenti`, ricorsiva sulle risposte): un commento rimasto col vecchio nome non si vedrebbe più dalla classe rinominata e una futura omonima lo erediterebbe.
    - La rinomina tocca **solo le card dell'anno corrente** (le legacy senza `annoScolastico` seguono, come in `cards.ts`): la 3A del 2025/26 non è la 3A del 2026/27, e riscrivere l'archivio falserebbe il record storico — è la stessa scelta già fatta per `classiPerAnno`.
    - **Analisi AI suddivisa per classe**: emette una chiamata per classe, e il throttle di `chiamaAI` è **globale e sincrono** (5s, all'istante di avvio). Il ciclo in `runAI` attende il resto della finestra con `attesaProssimaAI` (`src/ai-services.ts`, che delega il calcolo ad `attesaProssimaChiamata` in `src/ai-throttle.ts`) **prima di ogni classe, la prima compresa**: chi avvia l'analisi può aver appena usato un altro flusso AI. Se una classe fallisce a metà, le sezioni già calcolate **non si buttano**: `runAI` le salva prima di propagare l'errore e `aiErr` dice «Analisi parziale», perché rifare da capo costa una chiamata AI (5s di throttle) per ogni classe. La stessa finestra va chiesta prima di ogni chiamata in `valutaAperteProfAI`: il throttle vale anche fra studenti diversi. `attesaProssimaChiamata` limita l'attesa alla finestra stessa: con l'orologio risincronizzato all'indietro una chiamata sembra avvenuta nel futuro e l'attesa diventerebbe di un'ora.
    - **La validazione viene prima del throttle** in `chiamaAI`: una chiamata con parametri mancanti non deve consumare la finestra, altrimenti il tentativo corretto un istante dopo viene respinto con «Troppe richieste AI» e sembra un problema di rete. Vale anche per il login (`currentUser` assente o senza `getIdToken`): chi si riautentica subito dopo non deve trovare la finestra già spesa.

## Test

- Unit/integrazione: `src/**/*.test.{ts,tsx}` (jsdom, `globals: true`, setup `src/test-setup.js`). I test di integrazione in `src/integration/` usano il fake Firestore e hanno timeout 15s: non sono flaky per caso, prima di allungarli verifica che non sia un deadlock.
- **Le attese dei test non scendono mai sotto il default configurato.** `src/test-setup.ts` alza `asyncUtilTimeout` a 12s perché i test di integrazione montano l'app VERA (CardDetail lazy + i moduli delle modali) e sotto coverage il rendering rallenta: con il default di 1s i fallimenti erano sporadici in CI. Un `findBy…`/`waitFor(…, { timeout: 4000 })` però **scavalca** quel valore e rimette in gioco esattamente quel flake. Quindi non si passa `timeout` (si usa il default); un budget esplicito è ammesso solo se **più grande**, per flussi volutamente lenti. Vale anche per il budget dell'**intero test**: è lì che si vedono i test lenti **per progetto**, che hanno `{ timeout: 40000 }` per-test perché col `testTimeout` globale di 15s il margine è di qualche decimo di secondo e su un runner lento il fallimento sarebbe un «test timeout» generico invece dell'assert che dice cosa non è arrivato. I due casi misurati: i due test di auth col backoff deterministico da ~14,3s, e `src/integration/ai-403-flows.test.tsx` che aspetta davvero 5,2s per far scadere il throttle client-side (`AI_THROTTLE_MS`, condiviso via `_lastAiCall`), più il primo test di `src/integration/ai-elimina-flows.test.tsx` che paga il caricamento pigro di `CardDetail` con la coverage attiva (15,4s e 16s su un tetto di 15s: la CI è morta lì con «test timed out in 15000ms», un tetto, non un assert). **Prima di alzare un budget, misurare con `npm run test:budget`**: un test al 103% del proprio budget è il colpevole, mentre alzare il tetto a caso nasconde i test davvero lenti. Il primo test di un file di integrazione è il caso tipico, perché paga l'import che gli altri trovano già in cache.
- La regola la difende `src/attese-test-coerenti.test.ts`, su **tutti** i test di `src/` (non solo `src/integration/`): fallisce se un'attesa scende sotto `asyncUtilTimeout` e verifica che il default resti sotto il `testTimeout` di `vitest.config.js`. Riconosce le chiamate di testing-library con il lessico di `promise-utils.ts` (`sanitizza`), quindi `vi.waitFor` di vitest — che ha un suo default e non legge `asyncUtilTimeout` — resta fuori. Legge i numeri scritti a mano nel testo: un timeout calcolato (una variabile, un oggetto riusato) non lo vede, resta materia di review.
- E2E: `e2e/` con Playwright, Firebase finto, `baseURL http://localhost:5173` (più il preview di produzione su 4173). Un comportamento verificabile a mano va coperto da un test, non solo descritto. **Due progetti di browser**: `chromium` (Chrome di sistema in locale) e `webkit` (il motore di Safari — serve `npx playwright install webkit`). I file `*webkit.spec.js` girano solo nel progetto webkit. Coprire solo Chromium è stato un buco vero: la preview degli allegati si comportava diversamente su Safari e nessun test lo vedeva.
- L'harness E2E (`e2e/harness.html` + `harness-boot.ts`) di default monta l'app **senza `src/styles.css`** (comportamento e stili _inline_). Con `?css=1` il foglio viene importato dinamicamente: lo usa `e2e/contrasto-temi.spec.js`, che nei due temi legge i colori calcolati e verifica il contrasto WCAG di titolo/data della card e delle intestazioni del dettaglio. La base del tema è dichiarata dal test (`html,body`), perché l'harness non è l'app e senza base la catena dei fondi cade sul bianco del canvas — così il test misurava «bianco su bianco» (1,04) anche quando il testo era giusto. Il fondo della card si ricava dal token `--sb-surface`, il colore del testo dal nodo vero: è quest'ultimo che i bug sbagliavano (`rgba(255,255,255,.8)` su pannello chiaro). Con `?a11y=1` (da combinare con `?css=1`) la seed include una card con scadenza: `e2e/a11y.spec.js` audita così anche badge urgenza e countdown, che altrimenti non sarebbero mai nel DOM.
- `e2e/a11y.spec.js` fa girare **axe** su bacheca (griglia), **vista elenco** e dettaglio, nei due temi, con sei regole soltanto (`color-contrast`, `button-name`, `link-name`, `label`, `nested-interactive`, `target-size`): un audit completo produce decine di segnalazioni da valutare una per una, queste invece devono restare a zero. Le regole si aggiungono **una alla volta**, dopo che le precedenti sono a zero. Il test chiede `prefers-reduced-motion: reduce`: axe legge i colori calcolati, e durante l'animazione di apertura l'opacità intermedia produce falsi positivi (era successo: 7,4:1 e 10,3:1 segnalati come insufficienti). Ha già trovato un bug reale: il chip del tipo nel dettaglio usava `tema.color` con etichetta bianca e per «nota» (`#94a3b8`) stava a 2,5:1; ora usa `chipBg`, la variante scura prevista dal tema. Il test del toast esige che il nodo compaia tra quelli visitati da **`color-contrast`** (`passes` o `incomplete`: con lo sfondo a gradiente axe non decide, e in quel caso il contrasto è garantito dal test statico `contrasto-token.test.ts`), non solo che il toast sia nel DOM. Se si alza l'asticella, si aggiunge una regola qui alla volta.
- Due test statici chiudono i buchi che la suite normale non vede: `src/contrasto-token.test.ts` legge i token da `styles.css` e verifica coppie testo/superficie, il **pannello del dettaglio** (primo stop di `--sb-panel-grad`), le **bolle dei commenti** (`--sb-bubble`/`--sb-bubble-reply`) **e i badge di stato** (valori veri da `badgeStato`) nei due temi, con il fondo preso da `--c-bg` (il colore che `body` usa davvero: i valori fissi di prima erano più scuri/chiari del vero e rendevano il test ottimista); `src/token-usi.test.ts` scandisce i `.ts/.tsx` (esclusi i test) e fallisce se un `var(--sb-…)` non esiste in `:root`: un refuso come `--sb-lines` non produce errori, il testo ricade sul colore ereditato e nessun test di contrasto se ne accorge; `src/carddetail-hook-order.test.ts` fallisce se un hook viene dichiarato **dopo** `if (!c) return null` in `CardDetail` (React lancerebbe «Rendered more hooks than during the previous render»). Il parser dei token in `css-utils.ts` accetta le cifre nei nomi (`--sb-text-1`): prima le leggeva come `--sb-text-` e i token numerati erano invisibili anche a `css-coerenti.test.ts`.
- **Margine dei test**: `npm run test:budget` (`scripts/test-budget.mjs`) fa girare la suite con N processi che bruciano CPU (`--carico=N`, default metà dei core) e stampa la durata di ogni test in percentuale del suo budget: il `{ timeout: N }` della sua `it(…)` se c'è, altrimenti il `testTimeout` globale. Oltre l'80% è un avviso, al 100% il test è rosso. Serve a trovare i flake PRIMA che scattino, misurando invece di indovinare; è un cruscotto, non un gate — sotto carico la suite può essere rossa di proposito — quindi non va messo sulle PR. Gira di notte in `.github/workflows/test-budget-notte.yml` (cron `17 3 * * *`), che apre o aggiorna una issue se il budget fallisce: così un test che si avvicina al tetto si vede il giorno dopo, senza bloccare nessun merge.
- Il monitor quotidiano del login di produzione è `.github/workflows/login-monitor.yml` + `.github/scripts/check-login.mjs`; in locale lo script scrive screenshot (`login-monitor.png`, `login-non-carica.png`) che **non** vanno committati.

## Stile

- Prettier (`.prettierrc`): 2 spazi, single quote, `printWidth` 120, `trailingComma: es5`, parentesi sempre sugli arrow. Formatta solo ciò che tocchi.
- Commenti in italiano che spiegano il **perché** (il repository è pieno di note "perché" su bug passati: mantieni quello stile), non il cosa.
- Commit in stile conventional commits in italiano con scope: `fix(classi,login): …`, `build(docs): …`, `test(quiz): …`.
- I file del repository usano terminatori **CRLF**: mantienili quando modifichi file esistenti.
- **I due temi si esprimono con i token CSS** `--sb-text-1/2/3`, `--sb-line`, `--sb-surface`, `--sb-hero-bg` (`:root` scuro, `html[data-theme="light"]` chiaro), non con ternari `isLight ? … : …` negli stili inline: ogni ternario va scritto due volte e uno dimenticato sbaglia **un tema solo**, senza che nessun test lo veda dall'harness (che di default non carica il CSS: `?css=1` serve proprio ai test che lo guardano). Un punto rimasto fuori si riconosce così: nel tema chiaro il testo sparisce (era il caso di `FilterBar`).
- `.card-wrap` ha `content-visibility: auto` + `contain-intrinsic-size: auto 320px`: il DOM resta al suo posto (il drag&drop trova ancora `.card-grid [id^="card-"]`, i conteggi non si troncano) ma le card fuori schermo non pagano layout/paint. **Non rimuoverlo "per pulizia"**: è l'alternativa alla finestratura, che rompeva `useDragDrop`. Limite noto: Ctrl+F non trova il testo delle card non ancora renderizzate. Anche `.list-row` (vista lista) ce l'ha, con `auto 84px`: qui c'è **la misura**, 600 righe, un re-layout completo da ~17,3 ms a ~1,5 ms; sotto le ~50 righe la differenza è nel rumore.
- I pannelli di `CardDetail` (Quiz, AI, Partecipazione, DomandeLibere) restano import **statici**: il `lazy` è stato provato e scartato perché i quattro `Suspense` non hanno una condizione esterna — il componente è sempre montato, quindi il chunk si scaricherebbe comunque all'apertura di ogni card (quattro richieste in più e un pop-in, senza risparmio). Per renderlo utile servirebbe spostare la condizione quiz/prof **fuori** dal componente, senza duplicarla.
- `src/carditem-render-count.test.tsx` conta i **render effettivi** delle card (0 con oggetti riusati, 1 con una cambiata): è il contratto dell'ottimizzazione. Se passa a 30, il mapping dello snapshot è tornato a ricreare tutto.
- `src/stato-card.ts` è l'unico punto che decide il badge di stato della card (priorità fissata → nascosta → nuova; lo studente non vede NASCOSTA) e restituisce colori-token, non valori fissi. `src/utils/apertura-card.ts` misura l'apertura di una card (`segnaApertura`/`segnaCardPronta`, `durataApertura`, `mediaApertura`, `campioniApertura`): il numero finisce in Diagnostica (ultima, media, p50/p95 solo da 5 campioni in su), non in un log sempre attivo. `src/integration/apertura-card-wiring.test.tsx` copre il **collegamento** con `openCard` dalla vista elenco (dove non c'è `.card-wrap`, quindi una misura agganciata al click di `CardItem` non partirebbe): i test del modulo da soli non si accorgerebbero se `segnaApertura()` sparisse da `AppProvider`.
- Tre guardie statiche sui temi: `src/tema-token.test.ts` vieta i ternari `isLight ? … : …` (anche senza spazio prima di `?`, le negazioni e i confronti `=== true`/`=== false`) nei file già migrati ai token (allowlist: un solo ambra di ammonizione in `CommentsSection`); il regex non vede per ora confronti diversi (es. `== true`, `!== false`), altre variabili (`tema === 'light' ?`) o parentesi: se ne entra uno si aggiorna il pattern nello stesso commit insieme al caso sintetico. `src/colori-fissi-ratchet.test.ts` congela il numero di `rgba(255,255,255,` per file — le soglie si **abbassano** quando si migra un altro punto, mai si alzano. `src/touch-target.test.ts` congela i 24 px dei controlli (`minHeight`/`minWidth`, valori anche tra virgolette) e la geometria 24px dei pallini accento nel CSS: la classe di difetto dei `width`/`height` senza `min` resta coperta da axe `target-size`, che è lui ad aver trovato i pallini da 14px.
- `scripts/screenshot-temi.mjs` cattura bacheca, **vista elenco** e dettaglio con `styles.css` iniettato (l'harness E2E non lo carica) nei due temi: serve alla revisione manuale. Le immagini finiscono in `screenshots/` (risolta rispetto allo script, non alla CWD; `SB_SHOT_DIR` la cambia), ignorata da git. `e2e/visual.spec.js` è la regressione visiva vera, ma resta **opt-in** (`VISUAL=1`): le baseline dipendono da font e antialiasing della macchina, quindi vivono in `e2e/**/*-snapshots/` (ignorata) e si generano con `VISUAL=1 npx playwright test e2e/visual.spec.js --update-snapshots`. Non c'è un job CI che le confronta: su un runner Linux fallirebbe per il font, non per il layout.
- **`console.log` solo dietro `SB_DEBUG`** (`window.SB_DEBUG`, attivabile con `?debug=1` e persistito in `localStorage`): i `console.warn`/`console.error` restano per le cose azionabili, non per il rumore di un successo. Un log di diagnostica sempre attivo insegna a ignorare la console, e i fallimenti veri finiscono nello stesso mucchio.
